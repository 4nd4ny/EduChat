# Étape 7 — Publication, versionnement, quotas d'upload

**Dépend de :** Étape 3, Étape 4, Étape 5, Étape 6 · **Estimation :** 1-2 sessions

## Objectif
Permettre à un promptagogue vérifié de publier ou de mettre à jour ses tuteurs en moins de 5 minutes (exigences 3 et 8), avec le cycle de vie acté par le client : la publication crée un `draft` (« en construction »), invisible au catalogue mais testable dans le chat et partageable via une URL secrète `/p/essai/[share_token]` (simple lien non verrouillé, pour inviter des testeurs) ; la soumission le passe en `pending` ; l'approbation — par un admin OU un promptagogue vérifié — le rend `published` ; la dépublication le passe en `retired`. Un dépôt anonyme SANS compte est possible (`author_email NULL`) : il n'est publié qu'après validation admin et seul l'admin peut le supprimer. Côté serveur, les écritures sont protégées par le jeton Bearer HMAC de l'étape 6 (rôles relus en base/env à chaque requête), versionnées dans `prompt_versions`, et bornées par des quotas stricts : uploads texte uniquement, 256 Ko par prompt, 1 Mo cumulé par compte, 10 écritures/jour.

## Contexte et fichiers concernés
- `src/pages/api/prompts/[name].ts` — les squelettes POST/PUT/DELETE posés à l'étape 5 (renvoyant 401) prennent vie ici : création en `draft`, mise à jour versionnée, transitions de statut, suppression selon les droits, quotas, rate-limit. Écrit dans la base SQLite v2 de l'étape 4 (better-sqlite3, `DATA_DIR`, tables `users`, `prompts`, `prompt_versions`).
- `src/pages/publier.tsx` (à créer) — page de publication : bloc de vérification email (étape 6) OU dépôt anonyme explicite, formulaire complet avec gabarit socratique, import texte, quotas restants et prévisualisation.
- `src/pages/p/[name].tsx` (à créer) — page publique d'un prompt `published` : corps affiché en texte brut échappé, métadonnées, historique des versions, boutons « essayer » / « modifier ».
- `src/pages/p/essai/[token].tsx` (à créer) — page d'essai d'un `draft` retrouvé par son `share_token` : non verrouillée, jamais listée au catalogue, bandeau « en construction », prévisualisation chat, bouton « soumettre pour publication ».
- `src/chatSidebar/ChatSidebar.tsx:18-42` — pattern `react-dropzone` existant (`onDrop` + `useDropzone` avec filtre de type) à réutiliser pour l'import `.txt`/`.md` sur `/publier` (texte uniquement, tout autre type rejeté).
- `src/chat/AssistantMessageContent.tsx:59-69` — rendus personnalisés des balises `<thinking>` et `<encouragement>`, dont le gabarit socratique documente l'usage.
- `src/pages/api/completion.ts` — utilisé tel quel par la prévisualisation : le brouillon est passé en `system` dans le body de la requête, rien n'est persisté.
- Module DB de l'étape 4 (ex. `src/utils/db.ts`) — requêtes préparées à compléter pour `quota_bytes_used` (table `users`), `size_bytes`, `share_token` et l'historisation.
- Le champ `web_search` du prompt (recherche web désactivable par le promptagogue) est exploité à l'étape 8, et l'override par session (réglage prof) à l'étape 14 : hors périmètre ici.

## Tâches
1. Donner vie aux squelettes de `POST /api/prompts/[name]` : avec `Authorization: Bearer` valide (signature HMAC revérifiée à chaque requête, rôles relus en base/env), création du prompt en statut `draft`, version 1, `author_email` = email du jeton ; SANS jeton, dépôt anonyme accepté avec `author_email NULL`. Dans les deux cas, générer un `share_token` imprévisible (`crypto.randomBytes`, base64url). Rate-limit : 10 écritures/jour par compte (par IP pour l'anonyme).
2. `PUT` (mise à jour, réservée à l'auteur authentifié) : copier l'ancienne version dans `prompt_versions` puis incrémenter `version` ; sinon 403. Un prompt `published` mis à jour reste `published` : les conversations en cours conservent leur version (la bascule explicite est gérée à l'étape 8).
3. Transitions de statut (`PATCH` avec `{action}`) : `submit` (draft→pending, par l'auteur ou depuis la page d'essai pour un dépôt anonyme) ; `approve` (pending→published, réservé à un admin — `SECRET_ADMIN_EMAILS` — OU à un promptagogue vérifié `users.is_promptagogue` ; pour un prompt anonyme, admin UNIQUEMENT) ; `retire` (published→retired, auteur ou admin). L'UI de modération (file `pending`) arrive à l'étape 9 : ici, seules les règles serveur et des boutons minimaux.
4. `DELETE` : l'auteur authentifié supprime SES prompts ; l'admin peut tout supprimer ; un prompt anonyme n'est supprimable QUE par l'admin. Codes d'erreur stables (`ERR_FORBIDDEN`…).
5. Appliquer les quotas côté serveur : corps texte uniquement, `body` ≤ 256 Ko (262 144 octets) et cumul de `size_bytes` par compte ≤ 1 Mo ; en cas de dépassement, répondre 413 avec un code d'erreur stable (`ERR_PROMPT_TOO_LARGE`, `ERR_QUOTA_EXCEEDED`) ; tenir à jour `quota_bytes_used` dans `users`.
6. Créer la page `/publier` : bloc de vérification email de l'étape 6 tant qu'aucun jeton valide n'est présent, avec l'alternative explicite « proposer sans compte » (dépôt anonyme, publication après validation admin) ; formulaire (nom avec vérification de disponibilité en direct, langue, description, corps) ; import `.txt`/`.md` par drag-and-drop en réutilisant le pattern react-dropzone de `src/chatSidebar/ChatSidebar.tsx:18-42`, tout fichier non texte rejeté avec message clair ; quotas restants affichés.
7. Pré-remplir le corps avec un gabarit socratique (rôle du tuteur, règles « ne jamais donner la réponse », usage documenté des balises `<thinking>`/`<encouragement>` déjà rendues par l'interface), incluant un emplacement réservé clairement balisé « EXEMPLES À INTÉGRER » pour les exemples que le client fournira.
8. Ajouter la prévisualisation « tester avant de publier » : un chat qui envoie le brouillon comme prompt `system` dans le body de `/api/completion`, sans aucune persistance.
9. Créer `/p/[name]` (prompts `published` uniquement : texte brut échappé, métadonnées, versions, boutons « essayer » et « modifier » si auteur) et `/p/essai/[token]` (accès à un `draft` par `share_token` : non verrouillée, jamais listée, bandeau « en construction », bouton « soumettre pour publication »).

## Livrables
- `POST`/`PUT`/`PATCH`/`DELETE /api/prompts/[name]` avec statuts `draft`→`pending`→`published`→`retired`, droits (auteur / admin / anonyme) et quotas
- Pages `/publier`, `/p/[name]` et `/p/essai/[share_token]`
- Gabarit socratique (avec placeholder « exemples à intégrer ») + prévisualisation
- Dépôt anonyme opérationnel (validation admin obligatoire)

## Vérification
- [ ] Parcours complet dans un navigateur vierge : vérification email → gabarit pré-rempli → test en prévisualisation → création : le prompt est en `draft`, INVISIBLE sur l'accueil, mais accessible en fenêtre privée (sans jeton) via `/p/essai/[share_token]`.
- [ ] Soumission → `pending` (toujours invisible) ; approbation par un compte admin ou promptagogue vérifié → `published`, visible sur l'accueil en version 1.
- [ ] Republication avec le même nom depuis le même email → version 2, l'ancienne version est historisée dans `prompt_versions`.
- [ ] Tentative de mise à jour du même nom depuis un autre email → 403 ; suppression de son propre prompt par l'auteur → OK ; suppression par un tiers non admin → 403.
- [ ] Dépôt anonyme sans jeton → `pending` après soumission avec `author_email NULL` ; approbation par un promptagogue non admin → 403 ; suppression par un non-admin → 403.
- [ ] Envoi d'un fichier de 300 Ko → 413 avec code d'erreur clair ; publications successives dépassant 1 Mo cumulé → 413 ; import d'un fichier non texte (ex. `.pdf`) → rejeté.
